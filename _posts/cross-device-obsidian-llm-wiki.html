Building a Cross-Device, AI-Organized Obsidian Note System

August 17, 2026

I wanted a note system that follows me across my work PC, home PC, and phone, lets me write in a messy stream-of-consciousness style, and still ends up organized — without me doing the organizing. Here's what I actually built, including the mistakes along the way.

The goal

  • One Obsidian vault, edited from three devices (work laptop, home PC, phone)
  • Write raw, unstructured notes — todos, references, random thoughts, mixed languages
  • Let an LLM turn that mess into something structured and queryable later, instead of hand-filing everything into folders as I write

Part 1 — Syncing the vault with Syncthing

The sync layer is Syncthing on the two PCs, plus a Syncthing-compatible Android client on the phone, all pointed at the same folder ID — which is the same folder Obsidian opens as its vault.

The mistake: same Folder ID ≠ connected

Creating the folder with an identical Folder ID on all three devices doesn't sync them by itself. A shared Folder ID only tells Syncthing "these are meant to be the same folder" — two more things have to happen on top of that:

  1. Devices must be mutually added under "Remote Devices," with the connection accepted on both sides.
  2. The folder must be explicitly shared with each device, and the receiving device has to accept the share invitation that pops up.
Symptom to watch for If a file's context menu says "this file is not fully available on any connected device," Syncthing has no peer to push to — check both steps above first.

Android gotcha: storage permissions

Scoped storage can silently limit Syncthing to its own app-private directory instead of the public folder Obsidian actually writes to. If the folder looks connected but stays empty, check the app has full storage access and that the path picked is the real vault path.

Excluding .obsidian from sync

Editing on two devices around the same time produced conflict files — not on notes themselves, but on .obsidian/core-plugins.json, workspace.json, etc. These are per-device app state, not content. Fix: add an ignore pattern per device, in each folder's Syncthing settings: 

.obsidian

Ignore patterns are per-device, so this has to be added on each machine separately.

Part 2 — Folder structure: less is more

I originally over-designed the vault with folders like 01-personal, 02-projects, 03-todo, 04-reference, 05-daily. In practice that added friction to the "write raw" goal — hesitating over where something belonged instead of just writing it down. Simplified to: 

vault/
├── 00-inbox/        # everything goes here first
├── 04-reference/     # a small set of things worth keeping long-term
└── attachments/

Write daily, unsorted, mixed-language notes into 00-inbox, and periodically have an LLM re-organize the backlog rather than sorting by hand.

Part 3 — Getting an LLM to actually use the vault

A few ways to connect an assistant to a local vault, trading off differently by client:

  • Claude Code, run from the vault directory, gets direct read/write access with zero config — good for hands-on editing sessions.
  • Claude Desktop + a filesystem MCP connector works from a chat-style conversation, but desktop-only.
  • An in-Obsidian plugin works everywhere Obsidian runs, including mobile, independent of which chat client is in use.

Since I use Claude across web, mobile, and desktop interchangeably, the missing piece was specifically detailed content I never typed into a chat, but did write into the vault. For that, an in-vault plugin made the most sense.

Karpathy LLM Wiki plugin

I went with the Karpathy LLM Wiki plugin — an implementation of Andrej Karpathy's "LLM wiki" idea. It reads notes, has an LLM extract entities/concepts into linked wiki pages, and retrieves via graph expansion (Personalized PageRank over the link graph) rather than embeddings — no vector DB, no separate indexing pipeline.

Running it locally: two real bugs

1. Ollama models not showing up in the plugin, despite showing in Ollama's own GUI

A CORS issue, not a missing-model issue. The plugin runs inside Obsidian's app context (app://obsidian.md) and calls Ollama's local API to list models — Ollama only allows cross-origin requests from an explicit allowlist, and that origin isn't on it by default. 

OLLAMA_ORIGINS=app://obsidian.md*

Set as an environment variable, then fully restart Ollama (the service, not just the tray icon, if installed as one).

2. Raw model "thinking" text leaking into every response

Using a community-quantized GGUF (hf.co/unsloth/gpt-oss-20b-GGUF) pulled via Ollama's HuggingFace integration, responses came back with internal reasoning mixed into the output. gpt-oss models use OpenAI's "Harmony" format, separating an internal analysis channel from the final channel via a specific chat template — the official Ollama library build has it wired in correctly; some independently-uploaded GGUFs don't. This wasn't just cosmetic: the plugin's extraction depends on clean structured output, so the same bug was silently breaking ingestion too. 

ollama pull gpt-oss:20b

Where it landed

  • Notes sync reliably across all three devices, with .obsidian excluded to stop config-file conflicts
  • The vault stays a flat, low-friction inbox/ for daily writing
  • A fully-offline local LLM periodically turns that inbox into linked entity/concept pages I can query
  • Cross-language duplicate entities (e.g. "CRA" vs its Chinese name) are a known rough edge — the plugin's Lint wiki command is meant to catch and merge these

Takeaways

  • "Same Folder ID" in Syncthing is necessary but not sufficient — device trust and explicit folder sharing are separate steps people commonly miss
  • Exclude app config directories (.obsidian, .git, etc.) from file sync tools; they're per-device state, not content
  • If a local-model integration in an Electron-based app can't see your Ollama models, suspect CORS before anything else
  • For reasoning models like gpt-oss, prefer the inference tool's official model build over a community re-upload
